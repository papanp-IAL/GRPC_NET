Microservices Solution Blueprint

Proposed structure for the License, Dashboard and Auth services. Each service has its own API, BLL and DAL projects and owns one database schema. Services talk to each other over gRPC using shared .proto contracts. Every browser request first passes an API Gateway that checks the token and the user's permissions, using a shared Redis cache. Users sign in with company Active Directory (Microsoft Entra ID), and every component sends telemetry through OpenTelemetry. Click any folder or file in the tree to see what goes there.

Gateway (auth check, routing) Cache (Redis) API (Web API host) BLL (business logic) DAL (data access) Contracts (.proto) Common / repo files

    Reading the diagram

    • Every browser or partner request enters through the API Gateway. It checks the token and permissions (using Redis) before anything reaches a service. Services are not reachable from outside.
    • Solid grey arrows are project references inside one service: API → BLL → DAL → schema.
    • Dashed blue arrows are two-way gRPC links. Every service hosts a gRPC server in its .API and holds gRPC clients for the other services in its .BLL, so Dashboard can call Auth and Auth can call Dashboard, and the same for every pair.
    • Each service reads and writes only its own schema. Dashboard never queries the license or auth tables.
    • Contracts and Common are class libraries that every service references. They are never deployed by themselves.

    Most requests need no network call for the auth check: the token is verified locally, permissions come from memory, and the blocked-user check is one Redis lookup. After a role change, other gateway instances may use the old permissions for up to one minute.

    Rules for two-way gRPC

    • No compile-time cycles. Dashboard.BLL references Auth.Contracts and Auth.BLL references Dashboard.Contracts. Services never reference each other's projects, so two-way calls never create a project cycle.
    • No call loops in one request. If Dashboard calls Auth to answer a request, Auth must not call Dashboard back for that same request. Each call should end in a database read, not another hop back.
    • Deadlines travel with the call. EnableCallContextPropagation in Common.Grpc passes the original deadline and cancellation down the chain.
    • Ask with gRPC, announce with events. Use gRPC when the caller needs an answer now ("get permissions"). For "something happened" news ("user deleted, remove their widgets"), a message broker such as RabbitMQ or Azure Service Bus is a good later step, so the sender doesn't wait or fail if the receiver is down.
    • Service-to-service calls are authenticated too. Internal gRPC calls carry either the user's AD token (when acting for the user) or the calling service's own AD token (managed identity or client credentials). Common.Grpc adds the token and the receiving service validates it.

    Sign-in with Active Directory

    • Microsoft Entra ID (Azure AD) handles login. Users sign in with their company account, with single sign-on and MFA. Our services never handle passwords or issue tokens.
    • App registrations: one for the web app (signs users in with MSAL) and one for the platform API (api://company-platform). The gateway and every service validate tokens for that API with Microsoft.Identity.Web.
    • AD groups → app roles → permissions. AD groups (for example SG-License-Admins) map to app roles. The Auth service maps roles to fine-grained permissions such as license.read, stores them in the auth schema and caches them in Redis.
    • Users are keyed by their AD object id (oid claim) in every schema and cache entry, not by email, which can change.
    • Service-to-service calls use each service's own AD identity (managed identity or client credentials), or forward the user's token when acting for the user.
    • On-premises AD only? The same design works with AD FS issuing the tokens; only the AzureAd settings change.

    Telemetry

    • One library. The gateway and every service call AddCommonTelemetry("service-name") from Common.Telemetry. Nobody sets up telemetry by hand.
    • Traces follow one request through Gateway → Dashboard → License → Auth, including SQL queries and Redis lookups. Trace context passes automatically over HTTP and gRPC.
    • Metrics: request rate, errors and duration per endpoint and per gRPC method, cache hit rate, 401/403 counts, and .NET runtime health.
    • Logs: structured ILogger logs carry the trace id and the user's AD object id, so you can jump from a log line to the full trace.
    • Collector in the middle. Services send OTLP to an OpenTelemetry Collector, which forwards to Application Insights (or Grafana, Jaeger, Seq). Switching tools changes only deploy/otel-collector.yaml.
    • No personal data (names, emails) in logs or span tags.

    Example 1: a signed-in user opens the dashboard summary

    The token and permission checks happen once, in the gateway, using the shared cache. Services still verify the token but don't repeat the permission lookup. Every hop is recorded as a span in one OpenTelemetry trace, so you can see the whole request and where the time went in one view.

    1. Browser → Microsoft Entra ID

      The user signs in with their company AD account (single sign-on, plus MFA if your policy requires it). The web app uses MSAL to get an access token for api://company-platform. Passwords never reach our services.

    2. Browser

      Calls GET /api/dashboard/summary with Authorization: Bearer <token>.

    3. API GatewayAuthentication

      Checks the token's signature, issuer, audience and expiry locally with Entra ID's public signing keys, which are cached in memory. An invalid or expired token gets 401. No network call.

    4. API Gateway → RedisCache

      Blocked-user check: one lookup of blocked:{oid} (the user's AD object id). If the user was disabled in this app, the request gets 401 even though their AD token is still valid.

    5. API Gateway → cache → AuthAuthorization

      The route needs dashboard.view. The user's permissions come from memory, then Redis, and only on a miss from Auth.API over gRPC (then kept for 10 minutes). A missing permission gets 403.

    6. API GatewayRouting

      Applies the rate limit (429 if exceeded), then forwards the request to Dashboard.API with the same JWT and an x-correlation-id header.

    7. Dashboard.APIAPI

      Verifies the JWT again with Common.Auth (local and cheap), because services trust only signed tokens, never plain headers. Calls IDashboardService.GetSummaryAsync.

    8. Dashboard.BLLBLL

      Checks the data-level rule (does this user belong to this customer?), then calls License and Auth over gRPC in parallel, with deadlines, and reads its own widgets from the DAL.

    9. License.API → BLL → DALDAL

      Applies license rules and reads the license schema. It doesn't call Dashboard back while answering, so there's no loop.

    10. Dashboard.API → Gateway → Browser

      Returns JSON. If License was down, the summary still loads with a "licenses unavailable" flag instead of failing the whole page.

    Example 2: the reverse direction, Auth calls Dashboard

    The same pattern works the other way: here Auth is the caller and Dashboard is the gRPC server.

    1. Admin → API Gateway → Auth.API

      DELETE /api/auth/users/42. The gateway checks that the admin has user.delete.

    2. Auth.BLLBLL

      Disables the user in the auth schema, then uses PermissionCacheInvalidator to clear perm:42 and add blocked:42 to Redis.

    3. Auth.BLL → Dashboard.APIgRPC

      Calls DashboardGrpc.RemoveUserData using the generated client from Dashboard.Contracts. Dashboard.BLL deletes the user's widgets from the dashboard schema.

    4. Next request from user 42Cache

      The gateway finds blocked:42 in Redis and returns 401 straight away, even though the user's AD token hasn't expired yet.

    If the clean-up must not be lost when Dashboard is down, send it as an event through a message broker instead of a direct gRPC call.

    Ground rules

    • Controllers and gRPC services stay thin; all logic lives in the BLL.
    • The BLL depends on repository interfaces, so it can be unit-tested with mocks.
    • One DbContext, one schema, one migrations folder per service.
    • Cross-service data comes over gRPC, never through a shared table.
    • Proto changes are additive only. Breaking changes go into a new v2 package.
    • Package versions live only in Directory.Packages.props.
    • Every gRPC call sets a deadline; every service exposes /health.
    • All outside traffic enters through the API Gateway; service ports stay on the internal network.
    • The gateway does the coarse checks (logged in, has permission X). Data-level checks (does this user belong to this customer?) happen in the service BLL.
    • Cache keys and lifetimes are defined only in Common.Caching; only Auth clears permission entries.
    • gRPC can go both ways between services, but never in a loop within one request.
    • Users sign in with company AD (Microsoft Entra ID); services never see passwords.
    • Every service calls AddCommonTelemetry; no service has its own telemetry setup.

    Adding a new service (for example Billing)

    1. Create src/Services/Billing/ with Billing.API, Billing.BLL, Billing.DAL.
    2. Add Billing.Contracts with Protos/billing/v1/billing.proto if other services will call it.
    3. Create the billing schema and a database login limited to it; add the connection string to configuration.
    4. Reference Common libraries, register the service in deploy/docker-compose.yml, add a CODEOWNERS line and a path-filtered pipeline.
    5. Add tests/Billing.UnitTests and tests/Billing.IntegrationTests.
