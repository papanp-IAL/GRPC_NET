ModelMint Solution Blueprint

Folder structure and build rules for ModelMint v0.3: one .NET 10 Governance Plane (Host, Kernel, 13 modules, Worker) on one SQL Server 2022 database with a schema per module, a single Python 3.12 Analytics service with no database access, and an Angular 22 client behind a BFF. Every call between separate programs (Host, Worker, Python nodes and client systems) is gRPC with mTLS, in both directions; modules inside the Host call each other in-process. Installed natively on the bank's servers (IIS and Windows Services), no containers. Click any folder or file in the tree to see what goes there.

Angular client Host / Api (L2) Kernel (L3, L5) Application Domain Infrastructure / data (L8) Python Analytics Plane (L6) Shared, tooling, repo files

    Caller → serverService (.proto)CallsWhat it's for

    Host / Worker → Python nodemodelmint.analytics.v1.AnalyticsControlCancel, Health, CapabilitiesStop a running job, check nodes, see installed test packs

    Host → Workermodelmint.worker.v1.WorkerControlTriggerIngestion, VerifyChain, GetBacklogOperations console actions

    All links use mTLS on internal ports (Host 9443, Python 9444, Worker 9445), require a deadline, and carry OpenTelemetry trace context, so one trace follows a request across programs. Modules inside the Host never call each other through gRPC: that would split the single transaction (change + ledger + outbox) and add network hops for no gain. REST, file and database ingestion stay available for client systems that can't use gRPC.

    Flow 1: a validator approves a model version

    Every governed change follows the same path, so licence, permission, segregation of duties and the ledger can never be skipped.

    1. Angular client

      Sends POST /api/v1/approval/cases/{id}/decision. The browser holds only an HttpOnly session cookie and sends the CSRF header; it never sees an access token.

    2. ModelMint.Host · BFFL2

      Turns the cookie into the signed-in user (from OIDC or LDAP), with roles from sec.RoleAssignment and AD group mappings.

    3. Endpoint filtersL9

      Licence state (Read-only blocks writes), entitlement (Approval & Release needs Enterprise), then permission approval.decide with scope (legal entity, org unit).

    4. Approval.ApplicationCommand

      DecideApprovalHandler loads the case and checks record-level rules: is this user assigned to this case?

    5. Kernel · GuardEvaluator + SodServiceL3

      The transition's guards run (validation done, no open blocking findings), then SoD: the approver can't be the developer or the validator of this version. The outcome goes to sec.SodDecisionLog.

    6. One SQL transactionL5

      The state change (apr.ApprovalCase, wf.StateTransition), the ledger entry (ldg.LedgerSnapshot with its per-stream hash) and an outbox message all commit together, or none of them do.

    7. ModelMint.Workerasync

      Reads the outbox: links the entry into the global chain, updates rpt.ModelSummary, sends the Teams/email notification, calls each Host node's Notifications.Publish over gRPC so connected users see the change live, pushes the status change to client systems watching through ModelGate.WatchStatus, and forwards the audit event to SIEM.

    Flow 2: a test pack runs in the Analytics Plane

    Python never touches the database. It pulls work, proves who it is, checks its inputs and returns a signed result that .NET verifies before recording anything.

    1. Testing.Application

      A user starts a test run. tst.TestRun and ana.AnalyticsJob (status Queued) are written in one transaction with their ledger entry. The dataset's content hash is already recorded in tst.Dataset.

    2. Python node → Host (gRPC)lease

      A worker node calls AnalyticsJobs.Lease over gRPC with mTLS. SQL's READPAST locking hands each job to exactly one node, with a 2-minute lease.

    3. Verify job tokensecurity

      The lease includes a job token signed by the Host (Ed25519). The worker checks the signature, expiry, job id and licensed feature before doing anything.

    4. Load inputs from the Artefact Storehash check

      Reads the dataset files and recomputes their SHA-256. If it differs from the hash in the job, the job fails. Heartbeats keep the lease alive meanwhile.

    5. Run the test packisolated

      Runs in a separate process with resource limits (R1: scored data only; R2 sandbox: ONNX/skops only, no network). Writes result artefacts back to the store.

    6. Signed result enveloperesult

      Calls AnalyticsJobs.Submit with canonical JSON signed by the node's own Ed25519 key, plus the environment fingerprint and artefact hashes.

    7. Host verifies and recordsone transaction

      Checks the node signature and artefact hashes, then writes ana.AnalyticsJobResult, tst.TestResult rows and the ledger entry together. If the lease expires the job is re-queued; after the maximum attempts it is dead-lettered and an operator is alerted.

    8. Host → Python node (gRPC)other direction

      If a user cancels the run, the Host calls AnalyticsControl.Cancel on the node holding the lease, which stops the isolated process. The operations console uses Health and Capabilities on every node the same way.

    Flow 3: a bank's scoring engine checks the gate (B2B)

    Client systems that support gRPC use the ModelGate service from the client SDK. Others keep using REST, files or database feeds.

    1. Scoring engine → Hostserver stream

      At start-up the engine opens one gRPC channel (mTLS + its connector token) and calls WatchStatus for the models it uses. The stream stays open.

    2. CheckGateunary

      Before using a model version, the engine calls CheckGate. The Host answers from the Registry read model in milliseconds, so it can be called often.

    3. Kill switch in ModelMintgoverned

      A breach leads to a kill-switch decision in the Issues module: the usual guards, SoD, ledger entry and outbox message, in one transaction.

    4. Pushed to the engineseconds

      The Worker publishes the event, and the Host writes a StatusChange (Suspended) to every open WatchStatus stream. The engine stops using the version; the next CheckGate returns allowed = false. The time to acknowledge counts against the iss.KillSwitchEvent SLA.

    5. SubmitScoresclient stream

      At the end of the day the engine streams scored records. ModelMint tokenizes customer ids on arrival, runs the same envelope and content checks as file ingestion, and returns a BatchReceipt with control totals.

    Ground rules

    • Every governed change goes through a command handler, the Kernel's guards and SoD, and LedgerWriter, in one transaction.
    • Modules talk to each other only through ModelMint.Contracts: public interfaces for questions, outbox events for "something happened".
    • One DbContext per module, pinned to its own schema. Cross-schema foreign keys may exist in SQL, but code doesn't navigate across modules.
    • Every entity carries TenantId, LegalEntityId, audit columns and RowVersion; tenant filters are applied automatically.
    • Python never connects to SQL Server; .NET never runs analytics code.
    • Every call between programs is gRPC with mTLS and a deadline, defined in contracts/protos. Modules inside the Host never call each other through gRPC.
    • Ledger tables are append-only at the database level, not only by convention.
    • SHA-256 is for integrity (chains, content hashes). Secrets in data use HMAC with a key from the key adapter; encryption is TLS, TDE and key adapters.
    • Package versions live only in Directory.Packages.props.

    Adding a new module

    1. Create src/Modules/NewThing/ with NewThing.Domain, .Application, .Infrastructure, .Api.
    2. Pick a schema code, add NewThingDbContext with HasDefaultSchema, and its first migration.
    3. Register ledger event types in ldg.EventTypeRegistry and permissions in sec.Permission.
    4. Add its public interface and events to ModelMint.Contracts, plus AddNewThingModule() / MapNewThingEndpoints().
    5. Add the entitlement key to the licence tiers, a CODEOWNERS line, and the module to the architecture tests.

    Decisions to make before building

    Points found while comparing the v0.3 documents with this structure. Each one has a recommendation; none is a blocker if decided early.

    Conflict

    Python ledger code vs "no direct DB access"

    Governance doc p.4 lists existing Python mm-ledger with a "SQL Server ledger backend … same tables"; the boundary rule (p.6) says analytics never touches the database.

    Recommendation: all ledger writes go through .NET LedgerWriter. Keep mm_ledger for verification only, working on exported snapshots and digests, and remove its SQL backend.

    Spec needed

    One hash spec for .NET and Python

    "Same tables, same hash spec" across two languages.

    Recommendation: write contracts/hashing/canonical-hash-spec.md (RFC 8785 canonical JSON, 6-digit UTC timestamps, decimals as strings, lower-case GUIDs) plus test-vectors.json, and run both implementations against them in CI.

    Security

    Tokens for account numbers, PAN, Aadhaar

    CustomerToken / AccountToken are char(64), which looks like plain SHA-256.

    Recommendation: use HMAC-SHA256 with a per-tenant secret from the key adapter. These values have so few possibilities that plain SHA-256 can be reversed by trying them all.

    Inconsistency

    Result signature size

    ana.AnalyticsJobResult.Signature is varbinary(32) (HMAC size, shared secret); licence and usage signatures are varbinary(64) (Ed25519).

    Recommendation: an Ed25519 key per analytics node, so the Host can verify results but can never create one. Make the column varbinary(64) and add the signing node's key id.

    Performance

    Global chain on every write

    Per-stream and global chain written in the same transaction; ldg.LedgerHead is a single row.

    Recommendation: chain each stream inside the transaction, and let the Worker append the global chain in order to a separate append-only table (for example ldg.GlobalChainEntry). Otherwise every write in the system waits on one row, and append-only snapshot rows couldn't be updated with the global hash later anyway.

    Profiles M / L

    Multi-node behaviour isn't specified

    Two or more app nodes behind a load balancer.

    Recommendation: decide SignalR (sticky sessions + backplane), Quartz (clustered SQL store), cache (SQL distributed cache or Redis), and BFF session storage (shared ticket store) before increment 0 ends.

    Decided: gRPC

    gRPC between all programs: update the documents and check hosting

    Decision: gRPC for Host ⇄ Python, Host ⇄ Worker and client systems → Host. v0.3 still says "HTTPS Job API", and only REST/SDK, DB, files and MQ for client systems.

    Recommendation: update the runtime and integration pages, then confirm before increment 0: (1) Windows Server 2022+ if the Host stays in IIS, otherwise run the Host as a Windows Service on Kestrel; (2) the bank's load balancer and firewalls pass HTTP/2 end to end for client-system gRPC; (3) a certificate per node (Host, Worker, each analytics node) from the bank's internal CA, with a rotation process; (4) keep REST, file and database ingestion as well, because many bank systems can't speak gRPC.

    Wording

    "SHA-256 encryption"

    Raised in discussion, not in the documents.

    Recommendation: the documents use SHA-256 correctly, for integrity. If specific columns must be encrypted, add SQL Server Always Encrypted or AES-GCM through the key adapters. Licence certificates are signed (Ed25519), not encrypted.

    Data

    Tenant isolation

    Every table carries TenantId and LegalEntityId.

    Recommendation: EF Core global query filters in the shared DbContext base, backed by SQL Server row-level security, so a missed filter can't leak data between tenants or legal entities.
